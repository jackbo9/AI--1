## 2. 四步用户流程

### Step 1：填写活动信息

采用原型的必填／可选分区，不包含视觉创意输入。

- **必填**：活动主题、日期、时间、地点、参与对象。
- **多场次**：默认一场，通过“添加场次”展开第二场；沿用现有场次名称及日期、时间、地点结构。
- **可选**：补充说明、截止时间、联系人、活动规则、奖品、二维码链接。
- 移除单独必填的活动简介、两条亮点、注意事项和视觉描述要求；不通过编造默认内容满足旧 Schema。
- 活动主题直接作为海报主标题，AI 不改写。沿用 T01 单行标题限制，在调用模型前检查容量，超限提示用户返回修改。

字段投影：

| 输入 | 当前 T01 展示 |
|---|---|
| 活动主题 | 主标题，保留原文 |
| 日期、时间、地点 | 时间／地点组，展示所有场次 |
| 参与对象 | 参与对象组 |
| 补充说明 | 优化后进入顶部说明 |
| 活动规则 | 优化后进入现有第三组内容槽 |
| 二维码链接 | 确定性生成二维码 |
| 截止时间、联系人、奖品 | 保存到任务，标明“当前竖版暂不展示” |

未填写的可选内容保持为空；不补造说明、规则或奖品。缺失的说明和第三组正文不显示，保留现有其他槽位坐标。

### Step 2：AI 优化可选文案并确认

- 必填信息全部只读，包括活动主题。
- AI 仅优化已填写的可选叙述内容：补充说明、活动规则、奖品表达；不得虚构或改变数量、资格、条件等事实。
- 截止时间、联系人、二维码链接作为事实保留原值。
- 优化前后提供原文对照，用户可编辑可选叙述内容并确认；未投影到竖版的字段继续明确标注。
- 可选叙述全部为空时跳过文案模型调用，直接进入事实确认。
- 修改必填事实需返回 Step 1，重新创建任务；不覆盖既有任务和版本。
- **确认文案只保存内容快照并进入 Step 3，不启动视觉优化或生图。**

### Step 3：输入视觉想法 → AI 优化 → 确认生图

本步骤分为三个明确动作：

1. 用户用中文描述主体、动作、环境、风格和氛围。
2. 点击“AI 优化画面描述”，获得可编辑的中文描述。
3. 用户修改或再次优化后，点击“确认并生成主视觉”，才调用图片模型。

实现要求：

- 开放摄影、插画等风格的自然语言描述；不新增复杂风格库。
- 未指定风格时默认纪实摄影；用户已指定时不得被当前摄影常量覆盖。
- AI 优化依据为已确认内容的脱敏语义和本步骤视觉想法，不直接传入原始事实表单。
- 图片调用前再次脱敏，并由服务端注入品牌、T01 构图、安全区及禁止文字／Logo／二维码等约束。
- 用户编辑的是画面描述，不开放 HTML、CSS、坐标或固定模板约束。
- 用户改动原始视觉想法后，旧优化结果标记失效，需要重新优化。
- 优化失败时保留输入并允许重试；沿用本地规则生成描述的兜底时须明确标注，仍需用户确认。
- 生图阶段不得再次隐式调用 LLM 改写用户已经确认的描述。

### Step 4：查看结果、质量提示与下载

- 沿用当前预览机制：生成前是草稿示意，完成后展示服务端输出 PNG。
- 不迁入原型的 SVG／Canvas 导出逻辑。
- 质量区域沿用原型布局，删除固定 `10/10`、100 分及无真实依据的检查项。
- 只展示实际执行的检查及通过、警告、失败状态；不声称已经检测二维码可扫描性、画面语义等未实现能力。
- “只换主视觉”返回 Step 3，带入上一版描述；再次确认后生成新版本，保留旧结果。
- 未实现的保存草稿、历史记录等入口禁用并说明，不能显示虚假的成功提示。

## 3. 接口、契约与 fallback 调整

### 流程和数据

- 创建任务接口只接收活动信息，不再要求视觉意图。
- 修改 `POST /api/jobs/:jobId/confirm-copy`：保存确认快照，进入 `READY_FOR_VISUAL_INPUT`。
- 新增 `POST /api/jobs/:jobId/refine-visual`：保存视觉输入，异步优化并进入 `READY_FOR_VISUAL_REVIEW`；处理中使用 `REFINING_VISUAL`。
- 新增 `POST /api/jobs/:jobId/confirm-visual`：接收视觉草稿版本、用户确认的描述与幂等键，通过校验后进入生图阶段。
- 查询任务接口返回视觉输入、优化草稿、来源内容版本及当前阶段。
- 所有新增动作沿用任务所有者校验和幂等机制；并发或重复确认不得重复启动图片调用。
- 记录原始视觉想法、优化结果、最终确认描述、实际发送 Prompt、来源内容版本及模型信息。
- 用户重新确认文案后，旧视觉草稿失效，不能提交过期草稿生图。
- 当前任务 ID 写入页面 URL，刷新后通过查询接口恢复已保存阶段；不承诺恢复尚未提交的输入。
- 输入及内容契约提升版本，旧任务按读取兼容处理，不原地改写历史文件。现有双轨结构暂时保留，同步适配新字段；本轮不混入消融重构。

### 试用版 fallback

增加服务端 `READABILITY_MODE=strict|trial`，默认 `strict`，本次局域网 Demo 配置为 `trial`，不做用户可见开关。

`trial` 行为：

- 图片生成成功时始终保留该背景，不因对比度不足自动替换整图。
- 局部遮罩仅允许 `0`、`0.12` 两档。
- 优先选择最低强度的合格候选；均不合格时选择通过率最高的候选，再以 P05 对比度、较低遮罩强度作为稳定排序依据。
- 保留真实可读性结果，对比度不足显示“文字与背景对比度待优化”。
- 将下载资格与整体质量结果分开记录：增加按版本保存的 `exportAllowed` 和策略标识，不把可读性失败改写成通过。
- 基础硬检查通过、只有对比度警告时允许“下载试用稿”；下载接口读取该版本的资格，不按当前全局配置追溯放开历史失败结果。
- 事实被改写、字体或 Logo 加载失败、内容溢出等仍阻止输出。
- 图片服务真正失败时保留原有默认资产兜底，并与“图片已生成但对比度不足”明确区分。
- 严格模式维持现有阻断语义；不新增对比度模板变体。

同步更新 `HANDOFF.md`、`docs/ARCHITECTURE.md` 及 `docs/CONTRACTS.md`，明确本次试用策略替代此前的对比度强制阻断要求。用户已明确接受试用阶段暴露对比度不足，无需重复请求相同确认。
