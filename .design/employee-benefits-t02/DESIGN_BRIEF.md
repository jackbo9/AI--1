# 下一轮更新：员工福利 T02 与按场景分派的生成流程

日期：2026-09-07。状态：规划完成，未实施、未生图、未部署。

## 1. 目标与范围

在已有员工活动之外，开放“员工福利 → 下午茶”这一条真实可用的生成流程，首轮仅提供 T02 一款模板、1080×1920 PNG 一种规格。用户进入员工福利后直接使用 T02，不增加只有一个选项的模板选择步骤。界面明确“当前支持下午茶食品海报”。

员工通知、调查问卷继续显示待开放；周边折扣、体检、保险等福利子类没有对应契约和模板，本轮不承诺可用。后续按“场景事实 → 模板表单 → 独立 Prompt → 渲染与校验”逐项扩展。

不做通用表单搭建器、自由 Prompt 编辑器、自由画布、多模板推荐或新增模型供应商。沿用当前任务、Provider、身份、文件存储和不可变版本机制。

输入依据：

- Figma 母版： https://www.figma.com/design/HOcHU5gCOtyWPREqAEL04s/智慧引擎AI?node-id=325-200 ，本轮已读取结构与截图；名称为“Template / T02 员工福利，下午茶海报模版”。
- 用户附图：无花果、榴莲案例，共用同一品牌与排版骨架，食品底图可变；案例不代表两款模板，也不意味着福利仅限这两种食品。
- [设计方 Prompt 原文](./DESIGNER_PROMPT_SOURCE.md)：用户本轮完整提供，作为食品图生成设计输入，未授权本轮实际生图。
- [T01 多行计划](../../docs/T01_MULTILINE_IMPLEMENTATION_PLAN_2026-09-07.md)：相邻在途更新。本轮观察到其源码及测试已在修改，不覆盖、不回退，也不将其视为已验收。

当前分支为 `codex/update-image-generation-logic`。执行者先核对工作区和 T01 实际完成情况；本规划只写入本目录。

## 2. 模板契约提取

| 槽位 | Figma 已确认值 | 实现约束 |
|---|---|---|
| 画布 | 1080×1920，白底 | 最终固定尺寸，完整 PNG |
| 公司 Logo | x=72、y=80，280×82.518 | 复用品牌原始资产，保持比例 |
| 行政 Logo | 顶部右侧，76.5×76.5，外层左右 padding 72 | 使用已有资产并核对版本与黄色标识 |
| 标题 325:203 | x=72、y=297，宽936，MiSans Semibold 120，行高1.2 | 暂建议一行，最大行数属待验收策略；不继承 T01 三行 |
| 副标题 325:202 | x=72、y=466，宽820，MiSans Regular 28，行高1.45 | 暂建议一行；字号固定，超限提示精简 |
| 标题/副标题间距 | 466−(297+144)=25px | 可复用纵向内容流机制，但参数为 T02 的25px，不是 T01 的13px |
| 页脚 | 左“九号行政｜ADMINISTRATION”，右“员工福利 / BENEFITS”；18px、1.4、#75787B；底部80 | 代码绘制；含品牌信息，必须校验背景对比度 |
| 食品底图 | 母版节点无图片；用户案例给出全幅食品摄影 | AI 只生成无字底图，文字及Logo由HTML叠加 |
| 其他字段 | 无时间、地点、领取规则、二维码槽 | 不从活动表单继承，也不偷偷塞入图片 |

Figma 只给单行样例，没有完整容量声明。建议首轮标题输入安全上限40字符、副标题40字符，再用真实字体单行排版预检裁定容量；这些字符上限是实现建议，不是设计方要求。确认前在界面提示“请使用短标题 / 一句话亮点”，对超行内容给出可编辑错误，不改写事实、不裁切、不缩字。

## 3. 表单与内容权限

先锁定场景用途：这是一张福利主题传播海报，不是一张包含领取时间、地点和规则的完整通知。用户确需这些信息时，需补充支持相应槽位的模板，不能以后台保存代替传达。

| 用户字段 | 建议字段名 | 必填/默认 | 去向与权限 |
|---|---|---|---|
| 福利标题 | title | 必填 | 原文锁定，直接排版；不传图片模型 |
| 主题食品 | foodSubject | 必填 | 食品识别事实锁定；用于视觉，不允许AI换品种 |
| 主题亮点 | benefitHighlight | 必填 | 文案压缩的一句事实来源；品种、价格、数量、折扣等事实不可新增或改写 |
| 视觉状态 | foodStates | 可选；默认自然呈现 | 切开、堆叠、凝露、奶油、酥脆、冰镇等多选建议，选项需依食品适配；保留少量有长度上限的补充说明 |
| 主题色 | themeColor | 可选；默认食品本色 | 用于食品自然色彩和氛围；不能把固定浅色背景换成高饱和色块 |
| 副标题 | subtitle | 第二步生成、可编辑确认 | 只基于亮点精简，不创造“免费”“不限量”“低糖”等未提供主张 |

有多种食品时建议用户指定主食品，其他仅少量陪衬；可在视觉确认前展示推荐主食品，不能暗中丢弃已承诺的福利事实。视觉状态如“切开整杯咖啡”不适用时给出建议，不静默替换用户已选内容。

四步流程复用现有心智：填写福利信息 → 确认标题/副标题 → 确认食品画面方案 → 预览与下载。第三步展示结构化参数与简短中文描述，不要求业务人员粘贴设计方长 Prompt。首版可确定性编译这些字段，无需强制调用第二次 LLM 做画面扩写；如保留“AI 优化”按钮则为显式操作，不默认增添调用。

## 4. Prompt 产品化与冲突处理

使用独立 `t02-food-editorial-v1` Prompt 配置，按设计原文四个变量槽编译：foodSubject、visualHighlight、foodStates、themeColor。visualHighlight 从已确认福利亮点提取食品质感语义，不能把副标题原文、价格、员工信息、地点、二维码等业务事实送入图片模型。

分开记录原始设计 Prompt、版本化编译模板、原始输入、已确认文案、已确认视觉参数、最终发送 Prompt、模型/资产版本。编译模板可做字段映射及去重，但不得静默删减摄影要求、食品体量、留白和禁止项。

硬配置：画布比例、底部锚定、文字/Logo由代码绘制、背景颜色集合、模板字体及坐标。视觉生成目标：食品组合有效高度1300–1470、顶部Y=450–620、大主体与食品写实质感。视觉目标写入 Prompt 只能提高命中率，不能等同自动校验已通过。

需要明确处理的边界：

1. **食品与副标题冲突。** 副标题单行框延伸至Y≈506.6，Prompt允许Y=450起有食品。推荐默认食品最高点选Y=540（在原文推荐区间内），有效高度1380；同时明确标题/副标题实际矩形不得成为食品焦点或被明显主体侵入。若出现450–507边缘，需依据实际空间与对比度人工判定，不仅凭最高点判失败。T02 多行支持须另算安全区，不能直接套T01。
2. **纯白背景与主题色。** 主题色仅影响食品自然色和轻微氛围；白、暖白或极浅中性色背景保持固定。冲突输入需解释，不悄悄忽略。
3. **道具例外。** 原文允许必要道具但禁止cutlery。首版禁用刀叉/人物/手；饮品容器作为承载食品的必要物需纳入受控状态并确认，不能顺带生成咖啡厅、桌面布景。此为建议解释，不更改原文。
4. **页脚在食品区域。** 食品锚定底部可能使灰色页脚难读。检查实际页脚文字区域，失败阻止正式导出或重生成；不默认加遮罩、更换白字或重排页脚来冒充Figma一致。需要新变体时再记录设计决策。
5. **尺寸与请求载荷。** 当前 `seedreamPrompt` 最长2200字符、Provider使用全局IMAGE_SIZE。执行时测量替换变量后的最长载荷，按T02单独设合理上限并在请求前校验，不截断。确认现有供应商支持的输出尺寸；若先生成更高分辨率9:16，再确定性缩放至1080×1920，记录源尺寸/缩放，所有构图测量基于最终画布。不能只在Prompt中写尺寸而仍发出错误宽高比。
6. **降级资产。** 当前Provider失败会复制employee-activity-fallback.svg。T02必须走独立、经过认可的食品品牌兜底资产；缺资产时允许保留草稿但阻止输出成品，不能生成伪食品或拿活动插画顶替。批准的食品兜底资产是上线前待补输入。

首版不引入分割模型或付费视觉复核。DOM/像素程序可验证排版、尺寸、字体、文字对比度；食品边界、食欲感、畸变和无意生成文字须人工视觉审核，记录为manual/pending，不能将亮度阈值检测冒充食品语义检测。未来新增自动视觉审核应作为明确配置的能力单独规划。

建议新增路径：`src/contracts/benefits.ts`、`src/templates/employee-benefits.ts`、`src/templates/t02-layout.ts`、`src/providers/prompts/t02-food.ts`、`src/components/benefits-studio/`。建议一个明确的server侧场景策略注册表，绑定inputSchema、copy策略、visual策略、preflight、render、validate和fallback；客户端只读安全的展示/表单元数据，不导入Provider或密钥。

不把现有所有字段改为optional来兼容福利，也不把福利转成假活动。新文档使用可辨别联合类型，场景、模板和输出规格组合必须在服务端校验。复用任务状态、认领/幂等、版本追加、所有者验证和文件下载资格。

场景切换不修改已有任务的scene。新建/恢复任务按scene+template绑定表单、缓存键、预览和可用规格；未知scene必须明确拒绝。旧无scene任务只在确认属于旧活动结构时走适配。存储读失败不可静默丢弃不认识的任务再覆盖整个jobs.json，否则新增福利任务可能被旧活动归一化逻辑删除。

## 6. 交付与开放门槛

先完成T01在途验收，再按 TASKS.md 串行落地；公共Worker、Schema、存储改造不要与T01修改互相覆盖。

开发可用Fixture先跑通完整福利流程；开放入口前必须完成：母版尺寸/容量定稿、独立Prompt与场景路由、历史兼容、无花果/榴莲及至少一种非水果食品对照评审、认可的兜底资产、所有程序硬检查、人工视觉审核流程与PNG下载。通知/问卷仍待模板。

本计划不要求当前调用付费模型。真实生图样张是实施后的单独验收活动，应明确次数/费用，不自动循环到“好看”。源码发布按现有部署流程执行并分别冒烟T01、T02、历史任务；发布前备份业务JSON及资产。发布后出现新福利数据时不直接回滚到只会读取活动数据的旧存储实现，应优先关福利入口并保留兼容读取能力。
